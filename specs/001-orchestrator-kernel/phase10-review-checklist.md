# Phase 10 Review Checklist — 主 Agent / 子 Agent 协作体系

> 用途：给第二阶段方案 review / 评审 / 需求确认使用。
> 
> 目标：在进入实现前，把主 agent / 子 agent 的边界、流程、契约、风险、验收标准一次性对齐。

---

## 1. 范围是否明确

- [ ] 是否明确了第二阶段的目标不是“再加一个入口”，而是“主 agent + 单层子 agent 协作体系”
- [ ] 是否明确主 agent 负责控制面、子 agent 负责执行面
- [ ] 是否明确入口层只做标准化，不做编排
- [ ] 是否明确 CLI / HTTP / Feishu 都统一进入主 agent

## 2. 子 agent 边界是否明确

- [ ] 子 agent 第一版是否只允许单能力
- [ ] 子 agent 第一版是否必须是独立进程 / worker
- [ ] 子 agent 是否被限制为只做单一任务执行
- [ ] 子 agent 是否明确不负责路由 / 审批 / 全局取消

## 3. 路由方式是否明确

- [ ] 第一版是否采用 capability-based 规则匹配
- [ ] 第一版是否明确不使用 LLM 路由
- [ ] 路由结果是否可以审计和回放
- [ ] 路由决策是否有明确失败路径

## 4. 入口统一是否明确

- [ ] CLI 是否统一进入主 agent
- [ ] HTTP 是否统一进入主 agent
- [ ] Feishu 是否统一进入主 agent
- [ ] 三种入口是否共享同一内部请求模型

## 5. 通信契约是否明确

- [ ] 主 / 子 agent 请求模型是否已经定义
- [ ] 主 / 子 agent 响应模型是否已经定义
- [ ] cancel / status / health 协议是否已经定义
- [ ] 失败 / 超时 / 取消语义是否已经结构化定义
- [ ] 契约是否支持序列化、反序列化、审计、回放

## 6. 审计要求是否明确

- [ ] 是否明确第二阶段第一优先级是审计全链路与可回放
- [ ] 是否覆盖入口接收、路由、执行、失败、取消、回传
- [ ] 是否可以仅凭审计记录复原一次完整 trace
- [ ] 审计字段是否足够支撑后续 review 和排障

## 7. 流程是否清楚

- [ ] 是否能清楚描述完整链路：入口 → 主 agent → 子 agent → 回传 → 审计
- [ ] 是否能清楚描述取消流程
- [ ] 是否能清楚描述超时流程
- [ ] 是否能清楚描述失败流程

## 8. 范围控制是否到位

- [ ] 第一版是否没有引入多 capability 子 agent
- [ ] 第一版是否没有引入子 agent 再调子 agent
- [ ] 第一版是否没有引入 LLM 路由
- [ ] 第一版是否没有引入复杂多级任务树
- [ ] 第一版是否没有引入云端优先部署

## 9. 任务拆分是否合理

- [ ] 是否已经拆成设计 / 契约 / 主 agent / 子 agent / 入口联调 / 收尾几个阶段
- [ ] 是否能按 TDD 红 → 绿 → 重构推进
- [ ] 是否每个任务都有明确验收标准
- [ ] 是否每个任务足够小，便于 review

## 10. 验收是否可执行

- [ ] 是否能定义“做对了”的标准
- [ ] 是否能定义最小闭环成功条件
- [ ] 是否能定义回放成功条件
- [ ] 是否能定义失败、取消、超时的成功条件

---

## Review 输出建议

### 结论 A：通过
满足以下条件即可通过：

- 主 / 子 agent 边界清晰
- 通信契约清晰
- 审计要求完整
- 第一版范围可控
- 任务拆分足够细

### 结论 B：需要补充
如果存在歧义，优先补充：

1. 通信契约
2. 审计字段
3. 失败 / 取消 / 超时语义
4. 路由规则
5. 子 agent 单能力边界

### 结论 C：不通过
如果以下任一项仍不明确，则不进入实现：

- 主 / 子 agent 边界不清
- 入口与主 agent 职责重叠
- 子 agent 范围过大
- 审计无法回放
- 第一版引入过多复杂性

---

## 备注

- 该 checklist 仅用于 Phase 10 方案 review。
- 通过后再进入正式 TDD 任务实现。
- 若 review 中发现新的歧义，先回到设计文档修订，不直接进入编码。
